# Customer trust pages

`/privacy/`, `/terms/`, `/security/` and `/support/` are source-backed customer previews. They use the shared typography, navigation, brand metadata and footer, with a text-only project group. They introduce no tracking, forms, model calls, billing calls or provider writes. They remain `noindex,follow` with all existing route gates pending.

Generate with `npm run trust:build`; check generated bytes with `npm run trust:check`; run focused source tests with `npm run trust:test` and Chromium tests with `npm run trust:browser:test`. The browser CI job installs Chromium and requires the browser check; source-only CI and Vercel builds run the source tests. `website:build` includes trust generation, shared-shell generation and source-inventory regeneration. These pages do not alter billing or release flags.

## Copy and source boundaries

The config's source map links disclosures to the existing public implementation and release documents. The source scope is deliberately narrow:

- Clerk sign-in and service-side account, membership and subscription checks are access controls, not evidence that customer access is globally live.
- Current conversation text is sent only on Send; the interface holds interaction state without providing a saved conversation history. Hosting, identity, billing, security and accounting records are separate.
- Optional supported on-device dictation/playback sends no audio to Ad Astra. Device/browser behavior and installed support affect availability. There is no automatic microphone activation or cloud-speech fallback.
- Private cost/usage records contain identifiers and hashes rather than prompt content, as verified in the supplied private-accounting facts and companion contract. The public page does not expose those IDs, hashes, receiver details or evidence paths.
- Providers process data and may retain it under their policies/configuration. Ephemeral conversation state does not establish zero provider retention. Retention periods and request/deletion commitments remain unspecified until verified.
- Existing customers are directed to `/account/billing/` for account details and available Stripe-hosted management. No universal portal availability or cancellation outcome is promised.
- Terms provide sensible preview conditions and AI limitations. They invent no governing law, venue, refund restriction, retention period or paid contract. The pages claim neither legal approval nor a staffed support service.

## Readiness and finalization

`npm run trust:readiness` is a read-only pre-sales prerequisite check and is expected to exit **1** for this candidate. Normal generation/checks succeed while unresolved commercial evidence remains held. The validator requires the verified business record, complete verified/versioned policy disclosures, an operational contact with routing and support-service evidence, generated route presence, and acceptance under **every existing route gate** for all four routes. Phone/postal contact can satisfy the contact type; email is optional. A configured address/phone alone cannot establish operational support.

Policy fields are `version`, `effectiveDate`, `retentionNotice`, `rightsNotice`, `providerProcessingNotice`, `commercialNotice` and `evidenceRef`, with `status: "verified"` only when substantiated. They are used in place of the relevant holding copy. Operational support uses `status: "operationally-verified"`, `routingEvidenceRef`, `availabilityNotice` and `serviceEvidenceRef`. Email appears only with `emailStatus: "verified"` and `emailVerificationEvidenceRef`. All published text is escaped. Unknown fields should remain null, not guesses.

The validator checks evidence metadata, not the authenticity of the people or operating records behind it. The existing route ledger and its content, independent review and release authority gates remain authoritative; no new approval ledger or human process is introduced. Generated routes or links to their own HTML cannot satisfy evidence requirements. Tests use synthetic accepted metadata only to verify fail-closed behavior; they do not create real acceptance records.

The main release workflow must require this check before paid sales, alongside existing hosted acceptance and release controls. A passing trust prerequisite check does not enable billing, customer launch, regional availability, indexing or support operations. This increment does not modify the existing runtime billing gate. Finalization consists of supplying verified policy/contact/service details, reconciling the affected preview language, and completing the same existing route gates.
