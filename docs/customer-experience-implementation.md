# Ad Astra customer experience framework

## Direction and delivery boundary

Build one connected experience: discover Ad Astra, find a relevant product, understand the fit and limitations, create an authorized workspace, choose access on clear terms, complete useful work, and return with confidence.

This increment implements the discovery and orientation layer in the existing website source. It does not implement paid access or make a production-launch claim. The current public frontend is generated HTML/CSS/JavaScript with existing API handlers; the separate Next.js workspace prototype is not the production customer application. Do not describe this increment as a completed Next.js migration.

Canonical brand: **AD ASTRA**. Retain one authoritative source and its release history; do not create another hosted website or move the domain for this design exercise.

## Implemented now

- A homepage path into `/start/`, available in desktop and mobile navigation.
- Six intention-based directions mapped to the existing six product families.
- A readable workspace-style composition: intention, illustrative outcome, review requirements and next step.
- Six useful, downloadable written samples. These are static examples, not AI-generated responses or provider execution receipts.
- Seven connected journey stages, with preview versus future customer steps explicitly distinguished.
- URL selection and back-button support using allowlisted direction IDs; no free-text prompt or customer data in URLs.
- All examples and downloads remain usable with JavaScript disabled. No data collection, microphone activation, cookies, analytics, external requests, customer enrollment or payment is introduced.
- A pending route-evidence entry, conservative indexing and source-integrity checks. None constitutes independent approval.

The source contract is `config/customer-experience-framework.json`. Rendered artifacts are generated by `npm run journey:build`; editing the generated HTML or sample downloads directly will fail drift checks.

## Journey and acceptance framework

| Order | Customer outcome | Surface | Required implementation or acceptance |
| --- | --- | --- | --- |
| 1 | Understand Ad Astra and discover a relevant use | Home, approved search/ad landing pages | Truthful product positioning, reviewed artwork, clear next action; indexing and campaign activity only with approved evidence |
| 2 | Find the right product direction | Start, product and solution pages | Six mapped directions, relevant examples, honest availability, no dead-end CTA |
| 3 | Understand whether to proceed | Products, pricing, trust and support | Reviewed prices, limits, eligibility, cancellation terms, privacy, terms, support ownership and regional qualification |
| 4 | Enter the correct workspace | Sign-in and onboarding | Real identity provider integration; recovery, expiry, logout, server-side membership and two-tenant isolation QA |
| 5 | Obtain the right access | Checkout and subscription management | Approved offers, sandbox lifecycle QA, signed and replay-safe events, durable entitlements, cancellation and tax review |
| 6 | Receive useful value | Customer workspace | A supported task reaches the actual authorized model/tool, streams an honest response and supports reviewed persistence/export and failure recovery |
| 7 | Return and manage the relationship | Saved work, account, billing and support | Retrieval authorization, usage visibility, customer-controlled communications, incident/support procedures and verified recovery |

The local preview covers orientation and static samples, not the later live boundaries. The public operating-status surface remains the availability reference.

## Visual and interaction system

Use midnight navy, ice cyan, restrained champagne and generous typography from the existing shared design system. Neural artwork expresses connected intelligence; it is not runtime telemetry. Keep each screen's primary action obvious and the service-status disclosure close to it.

Use cinematic imagery to establish atmosphere, then provide calm, readable workspace surfaces for actual tasks. Continue using reviewed first-party assets; the existing story assets remain candidates for human visual and rights review. Do not borrow another brand's imagery or interfaces.

Future film work needs a selected final cut, truthful script, rights approval, poster image, captions where meaningful, explicit playback controls and a low-bandwidth fallback. No autoplay audio. Optional 3D must lazy-load, have an equivalent static view, obey reduced motion, expose a pause control and convey only real application events.

Future voice needs a deliberate microphone action, recording indicator, stop/cancel, understandable error states, retention disclosure and an equivalent text path. Never request microphone access on page load or narrate hidden model reasoning. Visualize documented workflow actions and retrieved evidence, not a fabricated thinking process.

## Technical alignment

Retain the current static marketing delivery while advancing the existing Next.js/React workspace in tested vertical slices. A migration is justified by accepted customer behavior, not by changing the stack label. Keep shared tokens, navigation, product IDs, availability contracts and reviewed content consistent across both surfaces.

The target customer boundary is:

`browser -> authenticated server -> authorized workspace membership -> entitlement and quota -> bounded model/tool -> durable result -> customer response`

Subscription events must reconcile into durable entitlements, not a client-controlled plan flag. CRM intake must resolve to the isolated Ad Astra tenant in the retained organization, deduplicate retries and honor consent and suppression. Public discovery pages must not contain credentials, private research data or operational records.

Anonymous preview selection does not enter CRM, create a lead or grant access. Introduce attribution only after privacy/consent review and separate product analytics from marketing permission. No cold-outreach schedule is created by this increment.

## Implementation order and ownership

1. **Product/design owner:** review this journey, product language, mobile composition and the six examples. Approve the actual visual/rights candidates before external publication.
2. **Website engineering:** complete product-detail continuity, trust/legal/support pages and approved pricing presentation. Finish performance and manual accessibility review; retain one canonical source.
3. **Identity/platform engineering:** complete onboarding and real server-side tenant membership. Verify sign-in, recovery, expiry, logout, forbidden access and two-tenant isolation using protected synthetic identities.
4. **Commercial engineering and finance:** implement and test the approved subscription lifecycle, provider event delivery and entitlement reconciliation. Confirm tax, refund, cancellation and dispute treatment before live payments.
5. **AI/workspace engineering:** complete one supported task end-to-end, including request authorization, quotas, streaming, cancellations, errors, storage and export. Expand to other products only after that slice passes.
6. **CRM/growth owner:** accept the isolated intake bridge and approved consent/suppression rules, then approve specific sender, audience, message, region, cadence and budget before activation.
7. **Media/design engineering:** deliver the approved film and optional bounded 3D/voice experience with privacy, rights, performance and fallback QA.
8. **Independent reviewer and release owner:** review the exact composite candidate, obtain final authorization, promote the tested deployment, then verify domain, customer flow and rollback. Existing GitHub connector access must be restored before the local changes can reach repository review.

A signed-in provider account is not acceptance of any of these flows. Do not mark a gate accepted merely because a configuration page is reachable. Internal-content visibility must be resolved before any CMS publication.

## Quality and measurement

Design targets, not measured guarantees: WCAG 2.2 AA; keyboard and screen-reader journeys; 320px through desktop layouts; text/no-JavaScript/reduced-motion fallbacks. Target p75 mobile LCP <= 2.5 seconds, INP <= 200ms and CLS <= 0.1 using representative field data once traffic and consented measurement exist.

Track the funnel only after its instrumentation is approved: qualified visit -> product fit -> signup completion -> checkout completion -> entitlement activated -> first useful task -> returning use -> retention. Define a first useful task as a completed authorized operation with a result the customer can review, save or export, not merely a chat message sent.

Report paid enrollments net of duplicates, cancellations and failed payments; do not count anonymous previews as subscribers. The 5,000-enrollments/month ambition is a business target, not activated demand or a revenue forecast. Report acquisition cost, conversion, net revenue retention, support demand, latency and failure rate from real accepted events, without promising global availability.

## Verification boundary

The new user story is: home -> choose an intention -> inspect the written sample -> download or explore its product -> review future access and current availability. Source and browser tests verify this path, six selections, safe unknown parameters, back navigation, downloads, no-script fallback and absence of external side effects.

The customer journey deliberately stops at the availability boundary. This report cannot substitute for authenticated AI, billing, tenant-isolation or provider QA. No live domain, DNS, indexing, billing, CRM, outreach, Sanity access policy or production deployment is changed by this framework implementation.
